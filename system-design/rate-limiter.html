Rate Limiter

Categoria: resiliência / edge · Dificuldade: clássico — a pergunta de abertura de praticamente toda entrevista de plataforma. Domine a mesa dos algoritmos e o “onde colocar” antes de desenhar qualquer caixa.

1. Requisitos (10 min)

Funcionais:

  • Limitar requisições por cliente (IP, API key, usuário autenticado) numa janela de tempo
  • Excedeu → 429 Too Many Requests com cabeçalhos que ensinam o cliente a se comportar (Retry-After)
  • Política por plano: free 10 req/s, pro 100 req/s (limite por key)
  • Opcional: pesos por endpoint (login mais rígido que GET de perfil)

Não-funcionais:

  • Overhead da decisão < 1 ms; memória pequena por chave
  • Distribuído: N instâncias atrás do LB aplicam a MESMA política — o limite é do cliente, não da instância (10 instâncias ≠ limite × 10)
  • Fail-soft do próprio limiter: se a fonte de decisão (Redis) cair, decide-se explicitamente deixa passar (fail-open) ou bloqueia (fail-closed)
  • Disponibilidade dos serviços protegidos: o limiter existe para proteger, não para ser mais SPOF que o protegido

Estimativas (guardanapo):

  • 10 M usuários ativos, 30% ativos por dia = 3 M DAU × 200 reqs/dia = 600 M reqs/dia ÷ 86.400 ≈ ~7.000 req/s média, pico 2–5× ≈ 35.000 req/s
  • Token bucket por chave ≈ 40 B (2 números: tokens + último refil) → 10 M chaves ≈ 400 MB — cabe num Redis modesto, sem desespero
  • Latência: decisão local em memória ~µs; via Redis +1 round-trip intra-DC ~0,5–1 ms — dentro do orçamento do gateway (que já tem ~10 ms de folga)

3. Alto nível

clientes → CDN/WAF → API Gateway (edge) ──► serviços internos
                     │
                     │  rate limiter middleware (em cada nó do gateway)
                     ▼
              Redis (decisão única e distribuída)
  • Edge/gateway: o limiter mora NA BORDA — bloqueia antes de o tráfego consumir autenticação, banco ou banda dos serviços internos (1ª trincheira contra abuso/DDoS de aplicação).
  • Middleware em cada nó: todo gateway aplica a mesma política olhando o Redis — a decisão é do cluster, não da instância.
  • Redis: estado central das chaves; uma requisição → um INCR/EVAL; o servidor serializa os comandos (single-thread) — sem corrida entre nós.
  • Lib (alternativa): limiter embutido na aplicação dá política por endpoint e evita o round-trip, mas cada instância replica o estado — só funciona se houver sticky por cliente ou se o erro de multiplicar o limite for aceitável. A resposta de sênior começa no edge e cita a lib como variação quando o requisito é “por endpoint com latência mínima”.

4. Deep dive (os três pontos onde a vaga é ganha)

a) A mesa dos algoritmos — token bucket vs janela fixa vs deslizante

Token bucket é o default porque bursts são comportamento legítimo (o usuário voltou de um café e apertou refresh 5×) e o custo por chave é fixo — um contador e um relógio, refil calculado por diferença de tempo:

import time

class TokenBucket:
    """Burst até `capacidade`, média `taxa_por_segundo`. Refil lazy: calcula
    quanto recarregou desde a última chamada — sem timestamps por req."""

    def __init__(self, capacidade: int, taxa_por_segundo: float):
        self.capacidade = float(capacidade)
        self.taxa = taxa_por_segundo
        self._tokens = self.capacidade
        self._ultimo = time.monotonic()

    def permitir(self, custo: float = 1.0) -> bool:
        agora = time.monotonic()
        # refil lazy: min(capacidade, saldo + tempo × taxa)
        self._tokens = min(self.capacidade, self._tokens + (agora - self._ultimo) * self.taxa)
        self._ultimo = agora
        if self._tokens < custo:
            return False
        self._tokens -= custo
        return True

b) Redis + Lua — a atomicidade que não se negocia

A decisão é check-then-act: “já estourou? não → incrementa”. Em duas chamadas Redis (GET + INCR) N gateways passam juntos: dois leem “restam 2”, os dois deixam passar e o contador vira 4. A saída é um script Lua executado dentro do Redis (EVAL) — o single thread do servidor garante que checar e somar é uma operação só:

-- Janela fixa atômica (testado contra Redis 8.8 em instância temporária:
-- limite 3 → respostas 1,1,1,0,0; TTL de 60 s montado no 1º INCR e NÃO
-- resetado pelos seguintes).
-- KEYS[1] = chave do contador (ex.: "rl:{cliente}:{janela}")
-- ARGV[1] = limite  ·  ARGV[2] = janela em segundos
local atual = redis.call('INCR', KEYS[1])
if atual == 1 then
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2]))
end
if atual > tonumber(ARGV[1]) then
    return 0        -- bloqueado
end
return 1            -- permitido

Janela deslizante exata na mesma filosofia, com ZSET (poda → conta → decide):

-- KEYS[1] chave do ZSET · ARGV[1] timestamp atual · ARGV[2] janela s
-- ARGV[3] limite · ARGV[4] id único da requisição (membro; nunca repete)
local agora, janela, limite = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', agora - janela)
if redis.call('ZCARD', KEYS[1]) >= limite then
    return 0
end
redis.call('ZADD', KEYS[1], agora, ARGV[4])
redis.call('EXPIRE', KEYS[1], janela)
return 1

(Testado: limite 3/janela 10 → t0, t1, t2 permitidos, t3 bloqueado; t11, t12, t13 liberam conforme os antigos expiram, t14 bloqueia de novo.)

c) Distribuído vs por instância — e o fail do Redis

  • Por instância (memória local): decisão ~µs, zero RTT — mas N instâncias = N × o limite. Mitigação: hash do cliente → instância fixa (perde o balanceamento, cria hot node, e ao morrer o nó o limite “reseta”).
  • Central (Redis): coerente de verdade (1 RTT ~1 ms por decisão — ok até ~100k decisões/s por instância de Redis; além disso cluster por hash da chave). É a escolha quando o requisito 2 (“mesma política no cluster”) é explícito — e no edge é o normal.
  • Redis caiu? Decisão explícita: fail-open (deixa passar + alarme) é o padrão de plataforma — um limiter que derruba o produto é pior que o abuso ocasional; fail-closed só quando o requisito é segurança dura (ex.: endpoint de senha sob ataque). Diga a regra e o porque antes de desenhar.
  • 429 e o ecossistema: o estagiário que derrubou o upstream não culpa o limiter — ele culpa o retry. O header Retry-After informado e respeitado pelo cliente (com jitter) transforma o 429 em sinal de cooperação, não de erro.

5. Trade-offs e gargalos

  • Quebra primeiro: Redis (latência + SPOF → réplica + fail-open) e, no sliding log, memória ∝ reqs na janela em spike (35k req/s × 60 s de log = milhões de membros — monitorar o ZSET).
  • Sacrifício consciente: token bucket em vez de exatidão (aceita burst curto de borda); 429 sem distinção de categoria (um 429 de login e um de GET pesam igual — contar 5xx e login em dobro fica para depois).
  • Com 10x mais tempo: cost-based limiting (peso por endpoint), GCRA (token bucket sem contador por chave), limite por conta com fallback por IP (NAT corporativo não pode pagar o pato de um único usuário), clusterização do Redis (failover + shard por hash da chave) e integração com o WAF para a borda grossa (DDoS) — o limiter de aplicação é a borda fina.
  • Pergunta-bônus comum: “e o mesmo cliente em 3 devices?” → limite por conta (chave rl:conta:{id}), não por device; IP só como camada extra de segurança contra contas roubadas.
