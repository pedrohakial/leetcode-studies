Chat / WhatsApp

Categoria: mensageria em tempo real · Dificuldade: avançado — a prova de fogo de quem já operou sistema a sério. As palavras que precisam sair da sua boca: sequência por conversa, store-and-forward, fan-out de grupo, receipts, presença — e cada uma com o porquê.

1. Requisitos (10 min)

Funcionais:

  • Mensagens 1:1 e em grupo (até ~1 mil membros), entregues em ~100–300 ms quando o destinatário está online
  • Presença: “online agora” e “última vez visto”
  • Ordem preservada POR CONVERSA — todos veem a mesma sequência
  • Offline → recebe tudo ao reconectar (store-and-forward), sem perder, sem duplicar, na ordem
  • Receipts: ✓ entregue / ✓✓ lida
  • E2E encryption: só as pontas leem; o servidor transporta ciphertext
  • Opcionais: “digitando…”, mídia (foto/áudio), push para o celular

Não-funcionais:

  • Escala de escrita pesada (~1:1 com leitura — raríssimo; redes sociais são 100:1, chat é o inverso)
  • Latência online < 300 ms; durabilidade: mensagem confirmada não some
  • Disponibilidade > 99,9% — chat morto é produto morto
  • Consistência: entrega única + ordem por conversa (nem global, nem casual)

Estimativas (guardanapo):

  • 500 M DAU × 40 msgs/dia = 20 B msgs/dia ÷ 86.400 ≈ ~230k msg/s média, pico 2–3× ≈ 500k/s
  • 1 KB por mensagem com overhead → 20 B × 1 KB ≈ 20 TB/dia ≈ 7 PB/ano → shard obrigatório (com retenção, 5 anos ≈ 35 PB)
  • Conexões simultâneas: 10% dos DAU ativos = 50 M WebSockets ≈ 20 KB por conexão = ~1 TB de estado de conexão nos gateways (50–200 nós)
  • Fan-out de grupo: média 50 membros; on-write puro → 230k × 50 ≈ 11,5 M entregas/s — o número que sozinho mata o on-write para grupos grandes

2. API + modelo de dados

WebSocket para o fluxo em tempo real + REST para o catch-up:

WS  → {tipo:"msg", conversa_id, texto, client_seq}
WS  ← {tipo:"ack",  conversa_id, server_seq}        # o servidor ordenou
WS  → {tipo:"receipt", conversa_id, server_seq, tipo:"lida"}
GET /conversas/{id}/mensagens?depois_seq=N          # reconnect / histórico
POST /conversas/{id}/mídia                          # upload (metadado no DB)

conversas(id, tipo '1:1'|'grupo', criada_em)
membros(conversa_id, usuario_id, PK(conversa_id, usuario_id))
mensagens(conversa_id, server_seq, remetente_id, texto, criada_em,
          PRIMARY KEY (conversa_id, server_seq))    -- shard POR conversa
entregas(conversa_id, server_seq, usuario_id, entregue_em, lida_em,
         PRIMARY KEY (conversa_id, server_seq, usuario_id))   -- receipts
presenca(usuario_id PK, estado, visto_em)           -- no Redis (TTL)
  • server_seq é do servidor, nunca do cliente: atribuído pelo único escritor da conversa (o shard dela) — aí a ordem é comparável entre clientes. O client_seq do cliente só serve para dedupe (duplo envio).
  • A PK (conversa_id, server_seq) torna o reenvio idempotente: same seq erro/upsert, nunca mensagem duplicada.

3. Alto nível

cliente → edge WS gateway (sticky) ──► serviço de mensagens (stateless)
   ▲                                      │  valida e atribui server_seq
   └───── entrega (WS/push) ←─────────────┤
                                          ▼
                              fila de entrega / notificação
                                          │
                                          ▼
                     banco sharded por conversa (mensagens, entregas)
                                          ▲
                              workers de fan-out (grupos)
   Redis: presença (TTL), cache de conversas quentes, contador de seq por
   conversa (contador de só escrita — seq de verdade vive no shard)
  • Gateway WS sticky: conexão tem estado (a thread que manda no socket); o reconnect cai no mesmo nó via L7 — estado do socket fora dos serviços.
  • Serviço de mensagens: sem estado de conexão — escala horizontal; é quem valida, ordena e escreve.
  • Fila de entrega: desacopla o pico de escrita (230k/s) da entrega ao destinatário; é o canal do store-and-forward e do push.
  • Banco sharded por conversa: todas as mensagens de uma conversa num shard só → a ordem é ORDER BY server_seq trivial, e o seq nasce lá.
  • Redis: presença e cache de calor; nunca é dono da verdade da ordem.

4. Deep dive (os três pontos onde a vaga é ganha)

a) Ordenação: sequência POR conversa, não global

Requisito real: “todo mundo vê a mesma ordem naquela conversa”. Então o relógio é por conversa — um contador monotônico atribuído pelo escritor único daquela conversa (o shard dela). Por que não:

  • Timestamp do cliente: relógios mentem, ordem aleatória no merge.
  • Seq global: escala mal (um contador único = gargalo) e é inútil — mensagem da conversa A não compete com a da B.
  • Seq por (remetente, conversa): serve só para dedupe local; não ordena os dois lados.

O reconnect pede depois_seq=N e recebe em ordem crescente; o cliente exibe na ordem do server_seq, não na ordem de chegada do WebSocket (que pode embaralhar via retry de rede).

# A regra em 20 linhas (testado): servidor atribui seq por conversa; offline
# cai na caixa (store-and-forward); reconnect entrega em ordem; receipts
# rastreiam entrega/leitura por (conversa, usuario).
class SimuladorChat:
    def __init__(self):
        self.prox_seq = {}
        self.caixas = {}            # (conversa, usuario) -> [(seq, texto)]
        self.ultimo_entregue = {}
        self.ultimo_lido = {}

    def enviar(self, conversa: str, texto: str, b_online: bool) -> int:
        seq = self.prox_seq.get(conversa, 0) + 1     # único escritor da conversa
        self.prox_seq[conversa] = seq
        chave = (conversa, "B")
        if b_online:
            self.ultimo_entregue[chave] = seq
        else:
            self.caixas.setdefault(chave, []).append((seq, texto))
        return seq

    def reconectar(self, conversa: str):
        chave = (conversa, "B")
        pendentes = self.caixas.pop(chave, [])
        for seq, _ in pendentes:                     # ordem = ordem do seq
            self.ultimo_entregue[chave] = seq
        return pendentes

    def marcar_lida(self, conversa: str, seq: int):
        self.ultimo_lido[(conversa, "B")] = seq

b) Fan-out de grupo: write vs read (o número decide)

  • On-write (cópia por destinatário): gravar o post na “caixa” de cada membro → ler é O(1). Custo da escrita = O(membros): 230k × 50 ≈ 11,5M gravações/s, mesmo 100% assíncrono, aquece o banco.
  • On-read (1 cópia + pull): a mensagem é única; cada membro busca/é notificado quando abre. Escrita O(1), leitura O(membros que puxaram).
  • Híbrido por threshold — a resposta de sênior:
    • grupos ≤ ~100 membros → on-write (caixa materializada por membro, leitura instantânea);
    • grupos grandes (10k+; é o caso do WhatsApp) → on-read: cabeçalho único + ponteiro para a mensagem; o membro puxa o corpo ao abrir.
    • O guardanapo vira o critério: diga o threshold e mostre a conta.
  • Receipts num grupo: escreve em entregas por membro (assimétrico — consequência honesta; batch por sessão de leitura).

c) Store-and-forward, receipts, presença e E2E

  • Offline: a mensagem (já com server_seq) vai para a caixa; quando o destinatário reconecta, GET ...?depois_seq=N puxa tudo em ordem — e o N vem do último seq entregue persistido, não da memória.
  • Receipts: ack do cliente → entregue_em; abrir a conversa → lida_em. Uma linha por (conversa, seq, usuario) — o volume cresce com o nº de membros e particiona junto com a conversa. Um “lido” em batch marca a faixa inteira (<= seq N), não mil linhas.
  • Presença: heartbeat do WebSocket (~30 s) atualiza o Redis com TTL; “visto por último” = último heartbeat. Fácil, preciso o suficiente.
  • Push: celular sem socket → APNs/FCM com “mensagem nova”; o corpo real só via pull encriptado.
  • E2E (alto nível, sem criptografia na entrevista): WhatsApp usa o Signal protocol — sessão por par com ratchet de chaves; para grupos, chave de sender keys compartilhada entre os membros. O ponto que você fala: o servidor transporta ciphertext e não lê o conteúdo — logo não indexa texto, não faz busca nem anti-spam sobre o corpo (a busca é encriptada no aparelho). O preço disso é arquitetural: a orquestração de fan-out, shard e cache opera sobre metadados (remetente, conversa, seq), nunca sobre o conteúdo.

d) Sharding de conversas

  • Shard por conversa_id — é a chave de TODAS as consultas quentes (mensagens WHERE conversa_id). 1:1 pode ser uma conversa determinística id = min(a,b)_max(a,b) → acha o shard sem índice extra.
  • O contador de seq só vive no líder do shard da conversa (transação): sharding por conversa dá ordem forte local, sem pagar ordenação global.
  • Grupo gigante é o hot shard: o on-read do item (b) já alivia a escrita — sem ele, um grupo de 100k derruba o nó dele.
  • Geo: shard por região de quem conversa (mensagem não atravessa oceano para ser salva); rebalance com consistent hashing.

5. Trade-offs e gargalos

  • Quebra primeiro: os gateways WS (estado + 50 M conexões; nó morre → reconexão em massa no vizinho) e o banco de mensagens na escrita (230k/s
    • receipts).
  • Sacrifício consciente: ordem forte por conversa = escritor único por shard (escrita da conversa serializa — ok, conversa individual escreve pouco); durabilidade por batch (fsync a cada 1–2 s → “confirmado” só o que já está no log persistido; ack-after-durable).
  • Gateway sticky vs stateless: conexão WS é longa e tem estado → sticky; o preço é failover não-transparente: reconexão rápida + pull do histórico (o depois_seq do item c resolve — perder o nó perde o socket, não a mensagem).
  • Com 10x mais tempo: busca de mensagens (índice encriptado local), mídia em CDN com upload direto por URL assinada (tira os bytes do servidor de mensagens), “digitando…” (canal efêmero, sem persistir), chamadas de voz (WebRTC, sinal da mensageria), reações (3ª tabela pequena ao lado de entregas), status (mensagem 1:N da própria conta).
  • Pergunta-bônus comum: “e se o mesmo usuário está em 2 devices?” → cada device tem sua própria fila de entrega/receipts; o seq da conversa é único e os devices sincronizam o ponteiro depois_seq.
